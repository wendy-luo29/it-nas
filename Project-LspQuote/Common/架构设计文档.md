# 架构设计文档

## 1. 总体结构

测试资产分为「交付物层」和「执行层」，分别存放在两个仓库：

```text
公共库（GitHub 组织）
├── it-nas               # 交付物层：本仓库，按 项目 / UR 批次归档
├── qa-skills            # 技能库：12 个流程技能，跨项目复用
└── qa-knowledge-base    # 知识库框架：规范、模板、knowledge_guard
          │
          ▼ submodule 引用
代码仓 ai-test-framework  # 执行层：pytest 脚本、Page Object、客户端、配置
```

## 2. 执行层分层

```text
tests/            用例层：pytest 脚本，按模块 → 功能分层，版本用 marker 标记
  └─ api/         接口测试
  └─ ui/          Playwright UI 测试
pages/            Page Object：一个业务页面一个类，异步等待集中在 env.yaml
api_clients/      HTTP 客户端，只负责传输，不做业务断言
utils/            公共能力：api_assertions、db（只读，autocommit=True）
data/             请求体基线数据
config/           分层配置：base.yaml → env.yaml → 模块子配置，深度合并
```

约束：

1. 客户端不做断言，断言统一走 `utils/api_assertions.py`。
2. 数据库查询参数化，禁止 SQL 拼接；游标用字典模式按字段名断言。
3. 计费金额断言用 `lsp_carrier_zone` + `lsp_carrier_rate` 实测值计算，不硬编码预期值。
4. 配置合并是深度合并，避免新增配置导致用例全量 skip。

## 3. 交付物层结构

```text
it-nas/Project-LspQuote/
├── 项目说明.md           项目简介、模块、历史需求索引
├── Common/               跨需求复用的稳定资产
│   ├── 用户使用手册.md
│   ├── 架构设计文档.md
│   └── 知识库/           规则、踩坑、术语、影响索引
└── UR-xxx-yyyyMMdd/      单需求批次，自包含
    ├── 版本说明.md
    ├── 用户需求/
    ├── 研发分析/
    ├── 接口文档/
    ├── 数据库文档/
    ├── 发布文档/
    ├── 测试报告.md
    └── 测试用例/{用例文件,脚本文件}
```

## 4. 知识库两层设计

| 层 | 位置 | 可变性 | 内容 |
| --- | --- | --- | --- |
| 证据层 | 代码仓 `requirements/`（逐步迁入 UR 目录） | 不可变快照 | 需求原文、接口契约、评审记录、AC 清单 |
| 结论层 | 代码仓 `knowledge/` | 可维护，需 front-matter | 业务规则、踩坑、术语、影响索引 |

结论层只在代码仓维护，交付物库 `Common/知识库/` 仅保留索引与基线 commit，避免双份漂移。

规则文件必须带完整 front-matter（`module` / `feature` / `status` / `confirmed_date` / `source_requirement`），无来源的规则不得写入。只有需求评审通过后才能写入结论层。

## 5. 技能流水线与门禁

```text
需求补全 → 需求评审 → 功能拆分 → 用例设计 → 用例评审
   → 脚本生成 → 代码评审 → 执行测试 → 报告生成 → 飞书通知
```

强制门禁：

| 环节 | 门禁 |
| --- | --- |
| 需求评审 | 必须落盘评审记录，含问题清单 / 结论 / 复审历史 |
| 用例设计 | 强制读模板；数值约束 100% 覆盖；计费场景必须输出费率事实表；单条用例禁止双向断言 |
| 代码评审 | 脚本评审通过才可执行 |
| 执行前 | `knowledge_guard.py --strict` 校验知识库与 case_id 双向对齐 |
| CI | 有效执行数必须 > 0，全 skip 判失败 |

## 6. CI 设计

托管 runner 无法访问内网环境，CI 只跑可离线验证的部分：

1. 知识库一致性（`--strict`，告警即阻断）
2. 用例可收集（导入错误、marker 未注册）
3. 离线 demo 冒烟（验证 pytest + Playwright 链路）

真实 API / UI 回归在内网自建 runner 执行。改造为多仓后，checkout 需拉取 submodule，`knowledge_guard` 使用双根参数（`--knowledge-root` / `--project-root`）。

## 7. 演进约束

1. 技能与知识库框架只放公共库，不在项目仓私改，避免多项目分叉。
2. 项目业务规则留在本库 `Common/知识库/`，不进公共库。
3. 用例文件与脚本分离：用例在交付物层，脚本在代码仓，索引里登记 commit 反查。
4. 需求批次目录只增不改，历史批次保持可交接状态。
